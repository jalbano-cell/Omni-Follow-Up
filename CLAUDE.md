# CLAUDE.md — OmniFollowUp

## What this is

OmniFollowUp is a multi-tenant estimate follow-up automation SaaS for local service businesses (plumbers, HVAC, contractors, etc). Each business signs up, walks through a short onboarding wizard (business info, connect Google, follow-up schedule, review), then tracks its own sent estimates, gets flagged which ones need a follow-up, drafts the follow-up message, queues it for human approval, and sends it via its own connected Gmail account once approved — plus shows at-risk revenue on a dashboard.

**This is NOT a general CRM and NOT a website builder.** Keep scope tight: estimates in, follow-ups suggested, revenue visibility, and approved sends out — resist adding generic CRM features (pipelines, deals, tasks, multi-object custom fields) to the Estimate/FollowUp side of the product. The one deliberate, bounded exception is the **Lead** object (`/leads`) — since OmniFollowUp is meant to be the single source of truth for every inbound inquiry, a Lead does carry lightweight CRM-adjacent capabilities on purpose: free-text assignment, internal notes, and an activity timeline (see the Non-goals section for the exact boundary). Don't let that scope creep back onto Estimates, and don't grow Leads into a second pipeline/deals system either.

**Sending is approval-gated and always will be.** The daily cron (`services/followupEngine.ts`) only ever drafts — it must never call `services/gmail.ts`. The only path to an actual send is `services/followupSender.ts`, invoked exclusively from the Follow-up Queue UI's Send/Retry action on a follow-up that's already `Approved` or `Failed`. If you're tempted to auto-send from anywhere else (a new cron job, a webhook, a batch script), don't — that's the one hard line in this product.

**Multi-tenant migration is in progress, in phases** (see `/Users/john/.claude/plans/eager-riding-volcano.md` for the full plan). All 5 phases — accounts/sessions/`businessId` scoping, onboarding + self-serve Google OAuth + real per-tenant sending, Calendar reminders, the reply inbox, and the analytics dashboard — are done. Future work should still be scoped as deliberately as these were, not bolted on ad hoc.

**Calendar reminders are output-only, always.** `services/calendarReminders.ts` creates a short reminder event when a follow-up is drafted (nudging the owner to go review it) and deletes it once the follow-up is sent or skipped. It never reads availability, never books anything, and every call is wrapped so a Calendar failure can never block drafting/sending/skipping — those are the actual point of each of those actions, Calendar is a side effect.

**The reply inbox surfaces replies, it never interprets them.** `services/replyMatcher.ts` matches incoming Gmail messages to an Estimate purely by `gmailThreadId` + the estimate's `customerEmail`, and only ever creates `Replies` records — it never changes an Estimate's status, never auto-drafts a follow-up, never marks anything resolved. A human reading the reply decides what happens next; keep it that way even as this feature grows.

**Analytics is computed live, not pre-aggregated.** `services/analytics.ts`'s funnel/revenue-trend/reply-rate functions re-scan `getEstimates`/`getReplies` on every page load — no snapshot table, no cron-computed rollups. Fine at current volume; if it ever becomes a real cost/latency problem, reach for a short-TTL cache (e.g. `unstable_cache`) before reaching for a new Airtable table.

**OmniFollowUp is the single source of truth for every inbound business inquiry (a Lead).** `POST /api/intake` is the one public, unauthenticated-by-session endpoint besides the cron — a business's own website contact form posts here directly (cross-origin, no cookie), authenticated by that business's `intakeApiKey` (Settings → "Website intake API") as a bearer token, resolved via `services/business.ts`'s `getBusinessByIntakeApiKey`. The three-file split (STEP 10 of the spec this was built against) is deliberate and should stay that way: `services/intakeService.ts` owns only HTTP-facing concerns for the request itself (validation, sanitization, honeypot spam check, in-memory rate limiting, the request-level audit log) and delegates to `services/leadService.ts`'s `createLeadFromSubmission` for everything a Lead's arrival triggers (the Airtable write, an `ActivityLog` entry, an in-app `Notification`, the owner-notification email); `services/activityService.ts` is the thin domain layer over the durable `ActivityLog` table that both `leadService.ts` and the dashboard's live feed read from. `app/api/intake/route.ts` stays a thin HTTP adapter. A Lead starts `status: "New Inquiry"` and is a *raw lead*, not an Estimate; a human reviews it on `/leads` (or its detail page, `/leads/[id]`) and explicitly clicks "Convert to Estimate" (prefills the New Estimate form, then calls `leadService.markLeadConverted`) or "Archive" — nothing here ever auto-creates an Estimate. The notification email goes out via the business's *own* connected Gmail (reusing `services/gmail.ts`) to its own `ownerEmail` — if Google isn't connected yet, the email step is skipped (logged, not thrown); the Airtable write, the in-app notification, and the email are independent best-effort steps after the Lead is saved, so a failure in any of them never turns a saved Lead into a failed API response. If the Airtable write itself fails, the full sanitized payload is logged via `logIntakeAudit` (console + best-effort `/logs/intake/*.jsonl`) before returning an error, so a submission is never silently dropped even though it didn't reach the dashboard.

**The intake rate limiter is in-memory and per-instance, not a hard security boundary.** It's a best-effort deterrent (per business+IP sliding window) against a form being hammered — it resets on cold start and doesn't share state across concurrent serverless instances. If abuse gets past it, reach for a shared store (e.g. Upstash/Redis) rather than trying to make the in-memory version "more correct."

**`ActivityLog` and `Notifications` are durable tables, a deliberate exception to "computed live."** Unlike Estimate/FollowUp/Reply analytics (still live-scanned, see below), a Lead's Timeline and the dashboard's notification bell need a real event history (created/converted/archived/assigned/note-added) and real read/unread state — that can't be synthesized from the Lead record alone. `services/activityService.ts`'s `logLeadActivity` is the only way an ActivityLog entry gets written, and it always also bumps the Lead's `lastActivityAt` in the same call — don't write to the `ActivityLog` table directly from anywhere else. Every `services/leadService.ts` lifecycle function (`archiveLead`, `assignLead`, `addInternalNote`, `markLeadConverted`, `createLeadFromSubmission`) logs its own activity entry; if you add a new Lead lifecycle action, log one too.

**AI Lead Intelligence analyzes and recommends — it never acts.** `services/aiInsightsService.ts`'s `analyzeLead` calls Gemini (`GEMINI_API_KEY`, model `gemini-2.5-flash`) once per Lead, synchronously from `leadService.ts`'s `createLeadFromSubmission`, and writes back a summary, category, priority (`High`/`Medium`/`Low` + reason), a rough opportunity value range + confidence explanation, a suggested next action, and a response urgency (`Today`/`24 hours`/`3 days`/`1 week` + reason). It must never send an email, contact the customer, or change a Lead's status — analysis and recommendation only, exactly as specified. It's best-effort and non-fabricating on failure: any error (missing key, network, bad response) leaves the Lead's AI fields untouched and sets `aiStatus: "failed"` rather than guessing. The business owner can edit any field (`leadService.ts`'s `updateAiInsights`), dismiss the recommendations (`dismissAiInsights` → `aiStatus: "dismissed"`), restore them, or force a fresh run (`regenerateAiInsights`) — every one of those is logged as its own ActivityLog entry. The two now-unused legacy fields this replaced (`priorityScore`, `suggestedFollowUpTiming`) were renamed to `_deprecated_*` in Airtable rather than deleted (the Meta API doesn't support field deletion) — don't resurrect them.

## Design system

Follow `ui-ux-pro-max.md` (in repo root) exactly — it is the canonical design reference (styles, palettes, font pairings, spacing scale, animation principles, component checklist). Do not override its philosophy.

Concrete choices made for this project (derived from that file, kept consistent across all screens):

- **Styles**: Dashboard (#34) + Card-First (#30) + Sidebar Navigation (#46) + Data-Dense (#23) for list/table screens, Minimalism (#3) as the base restraint, Onboarding (#42, step-by-step progressive disclosure) for the wizard.
- **Palette**: Neutral (Slate/Zinc) backgrounds, one primary accent — Indigo/Cobalt blue (`oklch(0.47 0.19 264)` light / `oklch(0.7 0.16 264)` dark), mapped to `--primary` in `app/globals.css`. Semantic status colors: `--success` (booked/won), `--warning` (at-risk/due), `--destructive` (lost). Never introduce more accent hues than this.
- **Font pairing**: #1 Geist / Geist Mono — already wired via `next/font/google` in `app/layout.tsx`.
- **Stack**: Next.js 15 (App Router) + TypeScript + Tailwind CSS v4 + shadcn/ui.
- **Spacing / type scale**: use the scale defined in `ui-ux-pro-max.md` (4/8/12/16/24/32/48/64/80/120/160, and the typography scale table). Don't invent new sizes.

Every screen must pass the Quality Bar and Component Checklist sections of `ui-ux-pro-max.md` before being considered done.

## Architecture rules

- `/app` — routes and page composition only. No Airtable calls or business logic directly in page components — call into `/services`. Every protected page/action calls `requireOnboardedBusiness()` (or, if it doesn't need the full record, `getCurrentBusinessId()`/`getCurrentSession()`) from `lib/session.ts` and passes `businessId` explicitly into service calls — never assume a global "the business." `requireOnboardedBusiness()` also redirects a business that hasn't finished the onboarding wizard to whichever step it's on — every new top-level authenticated page needs this same guard, not just data-fetching ones.
- `/components` — presentational + client-interactive UI, grouped by domain (`dashboard/`, `estimates/`, `follow-ups/`, `replies/`, `leads/`, `analytics/`, `layout/`, `auth/`, `onboarding/`, `settings/`) plus `ui/` (shadcn primitives, don't hand-edit generated files beyond what's needed). `recharts` is the one charting dependency (used only for the revenue trend line in `components/analytics/revenue-trend-chart.tsx`) — the funnel chart is plain CSS bars, since a proportional bar doesn't need a charting library. Don't add a second charting library; extend with `recharts` if a new chart type is needed.
- `/services` — all external I/O and business logic (Airtable client, business/tenant CRUD, follow-up generation engine, Google OAuth client, Gmail send/read clients, Calendar client, the approval→send orchestrator, the reply matcher, the Lead lifecycle, the ActivityLog domain layer, the intake request pipeline). Pages and API routes call services; services never import from `/app` or `/components`. Every tenant-owned table's functions in `services/airtable.ts` take `businessId` as an explicit first parameter — this is deliberate (not solved with implicit/ambient context) so tenant scoping is visible and auditable at every call site. Direct-id lookups (`getEstimate`, `getFollowUp`, `getLead`) additionally verify the fetched record's `businessId` matches the caller's, since `filterByFormula` scoping doesn't apply to a direct `.find(id)`. Keep `services/gmail.ts` (send), `services/gmailInbox.ts` (read), `services/googleOAuth.ts`, and `services/calendar.ts` pure transport (no Airtable/approval-state knowledge, parameterized with whatever tokens/addresses the caller passes in) — orchestration (retry, token decryption, Airtable sync, stage advancement, reminder create/clear, reply matching/dedup, Lead lifecycle side effects) belongs in `services/followupSender.ts`/`services/calendarReminders.ts`/`services/replyMatcher.ts`/`services/leadService.ts`, not in the transport files. `services/gmail.ts` (send) and `services/gmailInbox.ts` (read) are kept as two separate files on purpose, not one — don't merge them. Same reasoning applies to `services/intakeService.ts` (HTTP-facing: validation/rate-limit/spam/request audit) vs. `services/leadService.ts` (domain: what a Lead's arrival/conversion/archival/assignment/noting triggers) vs. `services/activityService.ts` (thin CRUD-adjacent layer over the durable `ActivityLog` table) — keep that three-way split when extending any of them.
- `/types` — shared TypeScript types/interfaces (`Estimate`, `FollowUp`, `Business`, `Lead`, `ActivityLogEntry`, `Notification`, `SessionPayload`, status enums). Composed read-model types that join multiple entities for one screen (e.g. `leadService.ts`'s `LeadDetail`/`LeadAiInsights`, `analytics.ts`'s `ActivityItem`) live next to the service function that builds them, not in `/types` — that's the existing precedent (`FollowUpQueueItem`, `ReplyInboxItem`, etc. are the exception, not `/types`'s norm).
- `/config` — constants (status lists, default follow-up cadence, Airtable table/field names, Google OAuth scopes/URLs, `APP_TIMEZONE`). `DEFAULT_FOLLOW_UP_CADENCE_DAYS` is a fallback — a business's own `followUpCadence*Days` fields (via `services/business.ts`'s `getEffectiveCadenceDays`) take precedence when set. `APP_TIMEZONE` (`America/Toronto`) is the one deployment-wide timezone, used both by the cron's local-hour check and Calendar reminder times — there's no per-business timezone field yet.
- `/lib` — small framework-agnostic-ish helpers (`cn`, formatting, date math). `lib/auth.ts` signs/verifies session JWTs and short-lived OAuth state tokens via `jose` (Edge-runtime compatible, used identically in `middleware.ts`, Server Actions, and the `/api/oauth/google/*` route handlers). `lib/session.ts` is how pages/actions resolve the current business — it independently re-verifies the JWT from the cookie rather than trusting middleware-forwarded headers. `lib/password.ts` hashes/verifies account passwords via Node's built-in `scrypt`. `lib/crypto.ts` encrypts Google refresh tokens at rest (AES-256-GCM, Node's built-in `crypto`) before they're written to Airtable, which has no field-level encryption of its own — never store a raw refresh token in an Airtable field. No shadcn re-generation beyond `lib/utils.ts`.
- `middleware.ts` (project root) — verifies the session JWT and redirects to `/login` if missing/invalid/expired. Excludes `/login`, `/signup`, `/api/follow-ups/generate`, and `/api/intake` only. It is a coarse authenticate-or-redirect gate — it is NOT the source of `businessId` for service calls (that's `lib/session.ts`), and it does NOT know about onboarding completeness (that's `requireOnboardedBusiness()`, checked per-page since it needs an Airtable read that doesn't belong in Edge middleware).
- **Google OAuth**: one shared OAuth client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) serves every tenant's consent flow — `services/googleOAuth.ts` is the only file that talks to Google's token endpoint. A business connects once (from onboarding or Settings) covering Gmail send/read and Calendar scopes together in one grant — don't add a second separate connect flow for Calendar later; reuse the existing refresh token. The OAuth `state` param is a signed, stateless JWT (`createOAuthStateToken`/`verifyOAuthStateToken` in `lib/auth.ts`) carrying `businessId` + `returnTo` — no server-side state store.

Keep TypeScript strict. No `any`. Handle Airtable/env errors at the service boundary with clear thrown errors — don't swallow them silently, and don't add defensive checks for cases that can't happen.

## Non-goals for now

- No CRM-style contact management beyond what's on an Estimate record. The reply inbox does NOT change this — replies are surfaced, never turned into tasks/pipelines/auto-actions.
- Leads have exactly two status transitions (`New Inquiry` → `Converted` via the explicit "Convert to Estimate" action, or → `Archived`) — resist adding a general status workflow/pipeline. `assignedTo` is deliberately a free-text field, not a linked-record assignment to a real team/user roster — there is no multi-user/team-member concept in this product yet, and adding one is a bigger decision than this field implies. `internalNotes` is a single running log (newest entry first, prepended by `services/leadService.ts`'s `addInternalNote`), not a threaded/multi-author comments system — don't add per-note authorship, edit history, or @mentions without a real reason to.
- No two-way scheduling/availability — Calendar integration is output-only (creating/deleting reminder events), never booking or checking availability, and never will be.
- No real-time reply notifications — sync happens once a day (piggybacked on the existing cron) plus on-demand via the "Check for new replies" button, not push/webhooks.
- Reply matching only works when a customer replies from the same address the estimate was sent to, on the existing thread — a reply from a different address or deep in an old part of a long thread won't be matched. Known v1 limitation, not a bug to silently "fix" by loosening the match (that would risk cross-estimate mismatches).
