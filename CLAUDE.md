# CLAUDE.md — FollowUpQuote

## What this is

FollowUpQuote is a multi-tenant estimate follow-up automation SaaS for local service businesses (plumbers, HVAC, contractors, etc). Each business signs up, walks through a short onboarding wizard (business info, connect Google, follow-up schedule, review), then tracks its own sent estimates, gets flagged which ones need a follow-up, drafts the follow-up message, queues it for human approval, and sends it via its own connected Gmail account once approved — plus shows at-risk revenue on a dashboard.

**This is NOT a CRM and NOT a website builder.** Keep scope tight: estimates in, follow-ups suggested, revenue visibility, and approved sends out. Resist adding generic CRM features (pipelines, contacts, deals, tasks) — if a feature doesn't directly serve "get this estimate followed up," it doesn't belong here.

**Sending is approval-gated and always will be.** The daily cron (`services/followupEngine.ts`) only ever drafts — it must never call `services/gmail.ts`. The only path to an actual send is `services/followupSender.ts`, invoked exclusively from the Follow-up Queue UI's Send/Retry action on a follow-up that's already `Approved` or `Failed`. If you're tempted to auto-send from anywhere else (a new cron job, a webhook, a batch script), don't — that's the one hard line in this product.

**Multi-tenant migration is in progress, in phases** (see `/Users/john/.claude/plans/eager-riding-volcano.md` for the full plan). Phase 0 (accounts/sessions/`businessId` scoping), Phase 1 (onboarding, self-serve Google OAuth, real per-tenant sending), Phase 2 (Calendar reminders), and Phase 3 (reply inbox) are all done. An expanded analytics page is the next phase. Don't build ahead of that plan's shape without reason.

**Calendar reminders are output-only, always.** `services/calendarReminders.ts` creates a short reminder event when a follow-up is drafted (nudging the owner to go review it) and deletes it once the follow-up is sent or skipped. It never reads availability, never books anything, and every call is wrapped so a Calendar failure can never block drafting/sending/skipping — those are the actual point of each of those actions, Calendar is a side effect.

**The reply inbox surfaces replies, it never interprets them.** `services/replyMatcher.ts` matches incoming Gmail messages to an Estimate purely by `gmailThreadId` + the estimate's `customerEmail`, and only ever creates `Replies` records — it never changes an Estimate's status, never auto-drafts a follow-up, never marks anything resolved. A human reading the reply decides what happens next; keep it that way even as this feature grows.

## Design system

Follow `ui-ux-pro-max.md` (in repo root) exactly — it is the canonical design reference (styles, palettes, font pairings, spacing scale, animation principles, component checklist). Do not override its philosophy.

Concrete choices made for this project (derived from that file, kept consistent across all screens):

- **Styles**: Dashboard (#34) + Card-First (#30) + Sidebar Navigation (#46) + Data-Dense (#23) for list/table screens, Minimalism (#3) as the base restraint, Onboarding (#42, step-by-step progressive disclosure) for the wizard.
- **Palette**: Neutral (Slate/Zinc) backgrounds, one primary accent — Indigo/Cobalt blue (`oklch(0.47 0.19 264)` light / `oklch(0.7 0.16 264)` dark), mapped to `--primary` in `app/globals.css`. Semantic status colors: `--success` (booked/won), `--warning` (at-risk/due), `--destructive` (lost). Never introduce more accent hues than this.
- **Font pairing**: #1 Geist / Geist Mono — already wired via `next/font/google` in `app/layout.tsx`.
- **Stack**: Next.js 15 (App Router) + TypeScript + Tailwind CSS v4 + shadcn/ui.
- **Spacing / type scale**: use the scale defined in `ui-ux-pro-max.md` (4/8/12/16/24/32/48/64/80/120/160, and the typography scale table). Don't invent new sizes.

Every screen must pass the Quality Bar and Component Checklist sections of `ui-ux-pro-max.md` before being considered done.

## Architecture rules

- `/app` — routes and page composition only. No Airtable calls or business logic directly in page components — call into `/services`. Every protected page/action calls `requireOnboardedBusiness()` (or, if it doesn't need the full record, `getCurrentBusinessId()`/`getCurrentSession()`) from `lib/session.ts` and passes `businessId` explicitly into service calls — never assume a global "the business." `requireOnboardedBusiness()` also redirects a business that hasn't finished the onboarding wizard to whichever step it's on — every new top-level authenticated page needs this same guard, not just data-fetching ones.
- `/components` — presentational + client-interactive UI, grouped by domain (`dashboard/`, `estimates/`, `follow-ups/`, `replies/`, `layout/`, `auth/`, `onboarding/`) plus `ui/` (shadcn primitives, don't hand-edit generated files beyond what's needed).
- `/services` — all external I/O and business logic (Airtable client, business/tenant CRUD, follow-up generation engine, Google OAuth client, Gmail send/read clients, Calendar client, the approval→send orchestrator, the reply matcher). Pages and API routes call services; services never import from `/app` or `/components`. Every tenant-owned table's functions in `services/airtable.ts` take `businessId` as an explicit first parameter — this is deliberate (not solved with implicit/ambient context) so tenant scoping is visible and auditable at every call site. Direct-id lookups (`getEstimate`, `getFollowUp`) additionally verify the fetched record's `businessId` matches the caller's, since `filterByFormula` scoping doesn't apply to a direct `.find(id)`. Keep `services/gmail.ts` (send), `services/gmailInbox.ts` (read), `services/googleOAuth.ts`, and `services/calendar.ts` pure transport (no Airtable/approval-state knowledge, parameterized with whatever tokens/addresses the caller passes in) — orchestration (retry, token decryption, Airtable sync, stage advancement, reminder create/clear, reply matching/dedup) belongs in `services/followupSender.ts`/`services/calendarReminders.ts`/`services/replyMatcher.ts`, not in the transport files. `services/gmail.ts` (send) and `services/gmailInbox.ts` (read) are kept as two separate files on purpose, not one — don't merge them.
- `/types` — shared TypeScript types/interfaces (`Estimate`, `FollowUp`, `Business`, `SessionPayload`, status enums).
- `/config` — constants (status lists, default follow-up cadence, Airtable table/field names, Google OAuth scopes/URLs, `APP_TIMEZONE`). `DEFAULT_FOLLOW_UP_CADENCE_DAYS` is a fallback — a business's own `followUpCadence*Days` fields (via `services/business.ts`'s `getEffectiveCadenceDays`) take precedence when set. `APP_TIMEZONE` (`America/Toronto`) is the one deployment-wide timezone, used both by the cron's local-hour check and Calendar reminder times — there's no per-business timezone field yet.
- `/lib` — small framework-agnostic-ish helpers (`cn`, formatting, date math). `lib/auth.ts` signs/verifies session JWTs and short-lived OAuth state tokens via `jose` (Edge-runtime compatible, used identically in `middleware.ts`, Server Actions, and the `/api/oauth/google/*` route handlers). `lib/session.ts` is how pages/actions resolve the current business — it independently re-verifies the JWT from the cookie rather than trusting middleware-forwarded headers. `lib/password.ts` hashes/verifies account passwords via Node's built-in `scrypt`. `lib/crypto.ts` encrypts Google refresh tokens at rest (AES-256-GCM, Node's built-in `crypto`) before they're written to Airtable, which has no field-level encryption of its own — never store a raw refresh token in an Airtable field. No shadcn re-generation beyond `lib/utils.ts`.
- `middleware.ts` (project root) — verifies the session JWT and redirects to `/login` if missing/invalid/expired. Excludes `/login`, `/signup`, and `/api/follow-ups/generate` only. It is a coarse authenticate-or-redirect gate — it is NOT the source of `businessId` for service calls (that's `lib/session.ts`), and it does NOT know about onboarding completeness (that's `requireOnboardedBusiness()`, checked per-page since it needs an Airtable read that doesn't belong in Edge middleware).
- **Google OAuth**: one shared OAuth client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) serves every tenant's consent flow — `services/googleOAuth.ts` is the only file that talks to Google's token endpoint. A business connects once (from onboarding or Settings) covering Gmail send/read and Calendar scopes together in one grant — don't add a second separate connect flow for Calendar later; reuse the existing refresh token. The OAuth `state` param is a signed, stateless JWT (`createOAuthStateToken`/`verifyOAuthStateToken` in `lib/auth.ts`) carrying `businessId` + `returnTo` — no server-side state store.

Keep TypeScript strict. No `any`. Handle Airtable/env errors at the service boundary with clear thrown errors — don't swallow them silently, and don't add defensive checks for cases that can't happen.

## Non-goals for now

- No CRM-style contact management beyond what's on an Estimate record. The reply inbox does NOT change this — replies are surfaced, never turned into tasks/pipelines/auto-actions.
- No two-way scheduling/availability — Calendar integration is output-only (creating/deleting reminder events), never booking or checking availability, and never will be.
- No real-time reply notifications — sync happens once a day (piggybacked on the existing cron) plus on-demand via the "Check for new replies" button, not push/webhooks.
- Reply matching only works when a customer replies from the same address the estimate was sent to, on the existing thread — a reply from a different address or deep in an old part of a long thread won't be matched. Known v1 limitation, not a bug to silently "fix" by loosening the match (that would risk cross-estimate mismatches).
