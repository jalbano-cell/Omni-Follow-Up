# CLAUDE.md — Omni Follow Up

## What this is

Omni Follow Up is a multi-tenant estimate follow-up automation SaaS for local service businesses (plumbers, HVAC, contractors, etc). Each business signs up, walks through a short onboarding wizard (business info, connect Google, follow-up schedule, business hours & time zone, review), then tracks its own sent estimates, gets flagged which ones need a follow-up, drafts the follow-up message, queues it for human approval, and sends it via its own connected Gmail account once approved — plus shows at-risk revenue on a dashboard.

**Product philosophy: as little technical setup as possible.** The onboarding wizard's only real dependency is connecting Google — no website changes, no API keys, nothing to configure on a third-party system. `services/business.ts`'s `saveGoogleConnection` turns on Gmail inbox monitoring (`monitorGmailInbox`) automatically the moment Google connects, making **Gmail the primary lead source**: the daily cron's `services/gmailLeadCapture.ts` scans the connected inbox for new customer inquiries (deduped by Gmail thread/message ID, skipping anything already on a known Estimate/Lead thread — see that file's doc comment) and creates a Lead (source `"Gmail"`) for each one, funneling through the exact same `leadService.ts`'s `createLeadFromSubmission` choke point as every other source. A business can still turn monitoring back off in Settings. The website Intake API, its API keys, and inbound/outbound webhooks all still work exactly as before — they're just reframed as optional "Advanced integrations" in Settings, never surfaced during onboarding, for businesses that want to wire up their own website or another system on top of the Gmail-first default.

**This is NOT a general CRM and NOT a website builder.** Keep scope tight: estimates in, follow-ups suggested, revenue visibility, and approved sends out — resist adding generic CRM features (pipelines, deals, tasks, multi-object custom fields) to the Estimate/FollowUp side of the product. The one deliberate, bounded exception is the **Lead** object (`/leads`) — since Omni Follow Up is meant to be the single source of truth for every inbound inquiry, a Lead does carry lightweight CRM-adjacent capabilities on purpose: free-text assignment, internal notes, and an activity timeline (see the Non-goals section for the exact boundary). Don't let that scope creep back onto Estimates, and don't grow Leads into a second pipeline/deals system either.

**Sending is approval-gated and always will be — for the Follow-up Queue.** The daily cron (`services/followupEngine.ts`) only ever drafts — it must never call `services/gmail.ts`. The only path to an actual send of an estimate/negotiation follow-up is `services/followupSender.ts`, invoked exclusively from the Follow-up Queue UI's Send/Retry action on a follow-up that's already `Approved` or `Failed`. If you're tempted to auto-send *that kind* of email from anywhere else (a new cron job, a webhook, a batch script), don't.

**The one explicit, narrow exception: the automatic Lead acknowledgment email.** `services/leadService.ts`'s `sendLeadAcknowledgmentEmail` sends an email to the customer with zero human review, immediately on lead creation — a deliberate product decision, not a bug or scope creep. It's kept safe to auto-send by being tightly constrained, not by being reviewed: `services/emailTemplates/acknowledgment.ts`'s `buildAcknowledgmentContent` is a deterministic template (no prices, no specific response-time promises, no invented facts, no named person) so the content structurally can't say anything wrong — there's no model output to review because there's no model. If you're extending this email (tone, content, when it fires), keep those constraints — don't let it drift toward the Follow-up Queue's job (quoting, negotiating, making commitments). Requires the business's Gmail connected, same as the owner-notification email; skipped and logged otherwise.

**Multi-tenant migration is in progress, in phases** (see `/Users/john/.claude/plans/eager-riding-volcano.md` for the full plan). All 5 phases — accounts/sessions/`businessId` scoping, onboarding + self-serve Google OAuth + real per-tenant sending, Calendar reminders, the reply inbox, and the analytics dashboard — are done. Future work should still be scoped as deliberately as these were, not bolted on ad hoc.

**Database: Supabase (Postgres) — Airtable has been fully retired.** Omni Follow Up started on Airtable, moved through a dual-write migration phase, and is now 100% Supabase; there is no Airtable dependency anywhere in the codebase (no `airtable` npm package, no `AIRTABLE_*` env vars). Where things stand:
- **Schema**: `supabase/migrations/*.sql` — `workspaces` (tenants, one per business, formerly "Businesses"), `users` (team members — see "Team members" below), `leads`, `estimates`, `followups`, `replies`, `activity_logs`, `notifications`. Column names are snake_case (`business_name`, `workspace_id`, etc.); the TypeScript layer (`services/db.ts`, `services/business.ts`) maps them back to the app's existing camelCase `Business`/`Lead`/`Estimate`/`FollowUp`/`Reply`/`ActivityLogEntry`/`Notification` interfaces, so nothing above the service layer changed shape. RLS is off — every access is server-side via the service_role key with `workspace_id` filtering in application code (every tenant-scoped function takes `businessId` as an explicit parameter; direct-id lookups additionally verify the fetched row's `workspace_id` matches, since there's no `filterByFormula`-equivalent scoping on a direct-by-id fetch).
- **The Supabase CLI is installed and linked** (`brew install supabase/tap/supabase`, `supabase login`, `supabase link --project-ref pqdlqlpesmoxklvalwgr`) — new schema changes go in a new numbered file under `supabase/migrations/`, applied with `supabase db push` (needs the project's DB password, from Project Settings → Database — not the same as the publishable/secret API keys). `supabase migration list` should always show local/remote in sync before pushing a new one.
- **`lib/supabase.ts`**: a single server-only client (service role key — never import this into a `"use client"` file) plus generic typed `insertRow`/`updateRow`/`selectById`/`selectWhere`/`deleteRow` helpers keyed off `types/supabase.ts`'s `Database` type. That file is generated (`supabase gen types typescript --linked > types/supabase.ts`), not hand-written — regenerate it after every migration instead of editing it directly.
- **`services/db.ts`**: the central data access layer for Leads/Estimates/FollowUps/Replies/ActivityLog/Notifications — same exported function names as the old `services/airtable.ts` it replaced, so every call site elsewhere in the app is unchanged. `services/business.ts` is the equivalent for the `workspaces` table (tenant/account CRUD).
- **Migration history, for context**: the cutover happened in stages — schema created, dual-write added (new Leads mirrored into Supabase best-effort while Airtable stayed authoritative and every read path stayed on Airtable), then a full backfill/rewrite once the mirrored data was verified: `services/business.ts` and `services/db.ts` rewritten against Supabase, all ~40 call sites' import paths updated, `services/supabaseSync.ts` (the dual-write mirror) deleted since it's no longer needed, and the `airtable_record_id` traceability columns dropped. The one real business account at cutover time was reconciled by hand (one field had drifted since its last mirror sync) before the rewrite shipped. If you ever see a reference to "Phase 4" or "dual-write" elsewhere (old commit messages, etc.), that's this same migration — it's since completed.
- **Session/ID note**: every `Business`/`Lead`/`Estimate`/etc. `id` is now a Supabase-generated UUID, not an Airtable record id. This changed the *value* of `businessId` for the one pre-existing account at cutover time — any session JWT minted before the cutover no longer resolves (a fresh login mints a new one against the new UUID, and everything works from there). Not an ongoing concern; noted here only so a stale-looking session bug isn't mistaken for something else.

**Calendar reminders (`services/calendarReminders.ts`) are output-only, always** — that rule is unchanged and still describes that file exactly: it creates a short reminder event when a follow-up is drafted (nudging the owner to review it) and deletes it once sent/skipped, never reads availability, never books anything, and every call is wrapped so a Calendar failure can never block drafting/sending/skipping.

**Superseded — appointment booking is now the Appointment entity, see the dedicated "Appointments" section below.** `services/appointmentBooking.ts` and the old `autoBookAppointments` instant-book bypass no longer exist; every parsed booking request becomes a durable `appointments` row that always requires owner approval. The mechanics referenced elsewhere in this doc (`parseRequestedAppointment`'s conservative date/time parsing, offering up to 2 open alternates when the requested slot conflicts, the Calendar API's separate enablement step below) are unchanged — only what happens with a free slot changed.

**Operational note discovered while building the above**: enabling the `calendar.events` OAuth *scope* in the consent screen does not enable the Google Calendar *API* on the underlying Google Cloud project — those are two separate steps. If Calendar reminders or appointment booking silently aren't working for a connected business, check whether the Calendar API is enabled at `https://console.developers.google.com/apis/api/calendar-json.googleapis.com/overview?project=<project-number>` before assuming it's a code bug — this had been silently failing (403 `SERVICE_DISABLED`, caught and logged, never surfaced) even for reminder creation until caught during appointment-booking testing.

**No AI/LLM dependency anywhere in the core product flow — by design, with one explicit, narrowly-scoped exception below.** Omni Follow Up originally called Google Gemini for lead analysis, appointment parsing, and acknowledgment content; it's been fully replaced with a deterministic rule engine (`services/automation/leadClassifier.ts`), a regex-based date/time parser (`services/automation/appointmentParser.ts`), and static email templates (`services/emailTemplates/`, assembled via `services/emailBuilder.ts`). There is no `GEMINI_API_KEY`, no per-lead API quota to manage for any of *that* — every lead scores and every acknowledgment email drafts the same way every time, for free, with no external dependency. Don't reintroduce an LLM here; if that scoring needs to improve, extend the keyword rules and lookup tables in `leadClassifier.ts`.

**The one exception: the inbound-email lead classifier (`services/leadClassification.ts`), Step 1 only — classify and log, nothing downstream depends on it yet.** This is a different pipeline stage than `leadClassifier.ts` above: it runs on a raw scanned Gmail thread *before* any Lead exists, to judge whether it's a genuine new-work inquiry at all (narrow definition — see the system prompt), not to score an already-created Lead's priority/category. It calls Claude Haiku (`@anthropic-ai/sdk`, model pinned in `services/anthropic.ts`, `ANTHROPIC_API_KEY` optional — missing key logs and skips rather than throwing) with prompt caching on the system prompt, and persists every decision to `lead_classifications` (migration `0016`) for review at `/admin/classifications`. Piggybacked into `services/gmailLeadCapture.ts`'s existing scan loop, reusing the already-fetched message. **Deliberately has zero side effects beyond that log row** — it never creates, blocks, or alters a Lead, and nothing (drafting, sending, follow-ups) reads its output yet. If a future phase wires its output into gating Lead creation or anything else, that's a new, explicit decision — don't assume it from this entry alone.

**The reply inbox surfaces replies, it never interprets them.** `services/replyMatcher.ts` matches incoming Gmail messages to an Estimate purely by `gmailThreadId` + the estimate's `customerEmail`, and only ever creates `Replies` records — it never changes an Estimate's status, never auto-drafts a follow-up, never marks anything resolved. A human reading the reply decides what happens next; keep it that way even as this feature grows.

**The /analytics page's four functions are short-TTL cached; the live dashboard's aren't.** `services/analytics.ts`'s `getFollowUpFunnel`/`getLeadSourceBreakdown`/`getRevenueTrend`/`getReplyMetrics` are each wrapped in `unstable_cache` (`ANALYTICS_CACHE_SECONDS` = 60) — Next.js's Data Cache, not a snapshot table or cron-computed rollup, per the guidance this replaces. Each still re-scans `getEstimates`/`getLeads`/`getReplies` under the hood (via a private `compute*` function); the cache just avoids repeating that scan for every viewer within the same 60s window on a page that's a trend view, not an actionable one. `getDashboardStats`/`getUpcomingFollowUps`/`getRecentActivity` (the main dashboard) deliberately stay uncached — those drive "what needs attention right now," where a minute of staleness is the wrong tradeoff. `getRecentActivity` also filters to a rolling 24-hour window (`timestamp >= now - 24h`) before sorting/slicing to `limit` — a display-only filter on the merged estimate/follow-up/reply/activity-log items assembled there, not a retention policy: `activity_logs` itself is untouched and still holds full history for the Lead Timeline (`services/activityService.ts`'s `getLeadTimeline`). If the analytics page's cache window ever needs shortening/lengthening, change `ANALYTICS_CACHE_SECONDS` in one place; there's no manual invalidation (no `revalidateTag` wiring) since staleness up to the TTL is an accepted tradeoff here, not a bug to route around.

**Omni Follow Up is the single source of truth for every inbound business inquiry (a Lead).** `POST /api/intake` is the one public, unauthenticated-by-session endpoint besides the cron — a business's own website contact form posts here directly (cross-origin, no cookie), authenticated by that business's `intakeApiKey` (Settings → "Website intake API") as a bearer token, resolved via `services/business.ts`'s `getBusinessByIntakeApiKey`. The three-file split (STEP 10 of the spec this was built against) is deliberate and should stay that way: `services/intakeService.ts` owns only HTTP-facing concerns for the request itself (validation, sanitization, honeypot spam check, in-memory rate limiting, the request-level audit log) and delegates to `services/leadService.ts`'s `createLeadFromSubmission` for everything a Lead's arrival triggers (the database write, an `ActivityLog` entry, an in-app `Notification`, the owner-notification email); `services/activityService.ts` is the thin domain layer over the durable `ActivityLog` table that both `leadService.ts` and the dashboard's live feed read from. `app/api/intake/route.ts` stays a thin HTTP adapter. A Lead starts `status: "New Inquiry"` and is a *raw lead*, not an Estimate; a human reviews it on `/leads` (or its detail page, `/leads/[id]`) and explicitly clicks "Convert to Estimate" (prefills the New Estimate form, then calls `leadService.markLeadConverted`) or "Archive" — nothing here ever auto-creates an Estimate. The notification email goes out via the business's *own* connected Gmail (reusing `services/gmail.ts`) to its own `ownerEmail` — if Google isn't connected yet, the email step is skipped (logged, not thrown); the database write, the in-app notification, and the email are independent best-effort steps after the Lead is saved, so a failure in any of them never turns a saved Lead into a failed API response. If the database write itself fails, the full sanitized payload is logged via `logIntakeAudit` (console + best-effort `/logs/intake/*.jsonl`) before returning an error, so a submission is never silently dropped even though it didn't reach the dashboard.

**The intake rate limiter is in-memory and per-instance, not a hard security boundary.** It's a best-effort deterrent (per business+IP sliding window) against a form being hammered — it resets on cold start and doesn't share state across concurrent serverless instances. If abuse gets past it, reach for a shared store (e.g. Upstash/Redis) rather than trying to make the in-memory version "more correct."

**`ActivityLog` and `Notifications` are durable tables, a deliberate exception to "computed live."** Unlike Estimate/FollowUp/Reply analytics (still live-scanned, see below), a Lead's Timeline and the dashboard's notification bell need a real event history (created/converted/archived/assigned/note-added) and real read/unread state — that can't be synthesized from the Lead record alone. `services/activityService.ts`'s `logLeadActivity` is the only way an ActivityLog entry gets written, and it always also bumps the Lead's `lastActivityAt` in the same call — don't write to the `ActivityLog` table directly from anywhere else. Every `services/leadService.ts` lifecycle function (`archiveLead`, `assignLead`, `addInternalNote`, `markLeadConverted`, `createLeadFromSubmission`) logs its own activity entry; if you add a new Lead lifecycle action, log one too.

**AI Lead Intelligence analyzes and recommends — it never acts.** (The name is legacy UI copy — see the note above, there's no actual AI involved anymore.) `services/automation/leadClassifier.ts`'s `analyzeLead` runs a deterministic rule engine (`classifyLead`) once per Lead, synchronously from `leadService.ts`'s `createLeadFromSubmission`, and writes back a summary, category, priority (`High`/`Medium`/`Low` + reason), a rough opportunity value range + confidence explanation, a suggested next action, and a response urgency (`Today`/`24 hours`/`3 days`/`1 week` + reason) — all from keyword matching and lookup tables, same output shape as before. It must never send an email, contact the customer, or change a Lead's status — analysis and recommendation only, exactly as specified. Classification itself can't fail; the only failure mode is the database write, which is caught and sets `aiStatus: "failed"` rather than leaving stale data. The business owner can edit any field (`leadService.ts`'s `updateAiInsights`), dismiss the recommendations (`dismissAiInsights` → `aiStatus: "dismissed"`), restore them, or force a fresh run (`regenerateAiInsights`) — every one of those is logged as its own ActivityLog entry.
## Appointments

**A first-class entity, deliberately decoupled from Estimates.** The `appointments` table (migration `0018`) has its own lifecycle (`requested` → `approved` → `completed`, or terminal `no_show`/`cancelled`) and optionally links to a `Lead` and/or an `Estimate` (both nullable, set-null on delete) — it can also exist fully standalone. Customer contact fields (`customerName`/`customerEmail`/`customerPhone`) are denormalized onto the row itself, same precedent as `Estimate`'s `customerName`/`customerEmail`, so an Appointment stays fully readable even if its linked Lead is later deleted. This replaced the old ephemeral `Lead.pendingAppointmentDateTime`/`pendingAppointmentDurationMinutes` fields (those DB columns still exist per this project's additive-only migration policy, but nothing reads or writes them anymore) and the old `services/appointmentBooking.ts` + `autoBookAppointments` instant-book bypass — **every parsed booking request now always requires owner approval**, no fast path skips it, since a wrong date/time/price at booking time is costly enough that "auto-book when free" was retired as a feature.

**Google Calendar is a display/scheduling layer only, never the source of truth.** `services/appointmentService.ts`'s `approveAppointment` creates the Calendar event on the owner's own calendar (`google_calendar_event_id` stored on the row) but never adds the customer as an attendee — no `attendeeEmails`/`notifyAttendees`, unlike the old pre-approval flow. The only way a customer hears about their appointment is Omni's own emails. Every scheduled send in the lifecycle below fires off the Appointment row's own timestamps, **never by reading Calendar back** — an owner renaming/moving/deleting an event must never cause a ghost send or a missed one.

**The five-step lifecycle, and which steps auto-send vs. require approval:**
1. **Instant pending-ack (auto, no approval)** — `services/appointmentService.ts`'s `createAppointmentFromLead` (called from `leadService.ts`'s `sendLeadAcknowledgmentEmail`, replacing the old `resolveAppointmentBooking` call) reuses `services/automation/appointmentParser.ts`'s `parseRequestedAppointment` unchanged; on a free slot it creates the `appointments` row (`status: 'requested'`) and immediately sends `services/emailTemplates/appointmentRequested.ts`'s copy — deliberately never implies the slot is locked in. If the requested slot conflicts, the existing alternates-offering behavior is unchanged (no Appointment row created — nothing's fixed yet).
2. **Owner approval → confirmation (human-approved, the one approval gate in this flow)** — `approveAppointment` creates the Calendar event **first**; only on success does it mark the appointment `approved` and send `appointmentConfirmed.ts`'s email (date/time/price/location/prep instructions, the last three owner-supplied at approval time via the `/appointments` page's Approve dialog, not auto-derived from anything). A Calendar failure is surfaced as a clear error and the appointment stays `requested` — never silently swallowed.
3. **Auto-completion (no email)** — `services/appointmentLifecycle.ts`'s `runAppointmentCompletionJob` transitions `approved` → `completed` once `scheduledEnd` has passed, unless the owner already flagged `no_show`/`cancelled` (via `/appointments`' own actions, which also best-effort deletes the now-stale Calendar event).
4. **Day-after review request (auto-send, pre-approved template)** — `runAppointmentReviewRequestJob` sends `appointmentReviewRequest.ts` once, one day after `scheduledEnd`, linking `business.googleReviewUrl` — skipped (logged) if that's unset, since there's nowhere to send the customer. Same ask for every customer, no gating happy vs. unhappy toward different destinations.
5. **Recurring rebook reminder (auto-send, pre-approved template)** — `runAppointmentRebookReminderJob` sends `appointmentRebookReminder.ts` (call to action: reply to the email — no dedicated public booking page exists in this app) `services/business.ts`'s `getEffectiveRebookIntervalDays(business, serviceType)` days after `completedAt` — business-wide default (`workspaces.rebook_interval_days`) with an optional per-service-type override map (`rebook_interval_overrides` jsonb, Settings' "Per-service overrides" textarea, `null` value = explicitly disabled for that service even with a default set). Never fires if the customer already has a future `requested`/`approved` appointment (`getFutureAppointmentsForContact`) — never nag someone already back on the calendar.

Steps 4 and 5 are piggybacked onto the same daily cron invocation as the follow-up/reply-sync/Gmail-lead-capture jobs (`app/api/follow-ups/generate/route.ts`), same Vercel Hobby-plan cron-schedule constraint as those (see the Architecture rules section's `/config` bullet). **The existing estimate follow-up cron stays draft-only, untouched** — these appointment auto-sends are a completely separate code path (`services/appointmentService.ts`/`appointmentLifecycle.ts`), not routed through `services/followupEngine.ts`/`followupSender.ts`.

**CASL compliance (Canada).** Every automated appointment email (steps 1, 4, 5 — plus the confirmation in step 2, for consistency, even though it isn't in the auto-send suppression list below) gets `services/emailTemplates/complianceFooter.ts`'s footer: business name, `workspaces.mailing_address` (Settings; omitted from the footer when unset — fill it in for real compliance), and an unsubscribe link. The unsubscribe token is a long-lived, no-expiration signed JWT (`lib/auth.ts`'s `createUnsubscribeToken`/`verifyUnsubscribeToken`) resolved by the public `app/api/unsubscribe/[token]/route.ts`, which calls `services/suppression.ts`'s `suppressContact` and redirects to the static `/unsubscribed` confirmation page. **Suppression is checked before every automated send** (steps 1, 4, 5 — `isContactSuppressed`) and, once set, kills the entire downstream sequence for that contact (review request AND rebook reminder both check it independently), not just the one email that triggered it.

**Idempotency.** Every automated send sets its own `*_sent_at` guard (`review_request_sent_at`/`rebook_reminder_sent_at`) on send *attempt*, regardless of outcome — best-effort, no retry, matching this app's existing philosophy for every other automated email (the lead acknowledgment doesn't retry either). This makes every lifecycle job safe to re-run: nothing depends on the cron firing at an exact time, only on the Appointment row's own timestamps having passed.

**The pre-appointment reminder is the one exception to "auto-send" in this file — it's approval-gated, deliberately.** `services/appointmentLifecycle.ts`'s `runAppointmentReminderDraftJob` (piggybacked on the same cron invocation as the other three jobs) drafts (never sends) a reminder once an `approved` appointment enters its reminder window (`services/business.ts`'s `getEffectiveReminderHoursBefore`, default 24h, business-overridable in Settings), setting `reminder_status: 'pending'`. From there it's the Estimate Follow-up Queue's Approve/Edit/Skip/Send shape, not the auto-send shape: `services/appointmentService.ts`'s `approveReminder`/`editReminderMessage`/`skipReminder`/`sendReminder`, surfaced on `/appointments` via `components/appointments/appointment-reminder-section.tsx`. `sendReminder` is the only path that emails — not gated by the suppression list (same "confirmation email" precedent: a human is explicitly choosing to send about a specific already-approved booking). The drafted `reminder_message` deliberately excludes the compliance footer (`services/emailTemplates/appointmentReminder.ts`'s `buildAppointmentReminderBody` returns body only) since it may be edited before sending — the footer (with a fresh unsubscribe token) is appended at send time instead, same split `services/followupEngine.ts`'s `draftFollowUpMessage` already uses for the Estimate side.

**Per-client product mode — agency-set, like status.** `workspaces.product_mode` (`types/business.ts`'s `WorkspaceProductMode`: `'estimates_only' | 'appointments_only' | 'both'`, defaults `'both'`) lets the agency restrict a workspace, via `/admin`, to just the Estimate/Follow-up pipeline, just Appointments, or both — set alongside `status` in both the per-workspace activation form and the new-workspace provisioning form (`app/admin/actions.ts`'s `updateWorkspaceEntitlementAction`/`provisionNewWorkspaceAction`). **Leads are never gated by this** — they're the shared inbound funnel both surfaces are built on (a booking request is *parsed from* a Lead's message), not an "Estimates feature." Enforcement is a hard gate, same posture as `hasActiveEntitlement`: `lib/session.ts`'s `requireEstimatesEnabled()`/`requireAppointmentsEnabled()` (composing on `requireOnboardedBusiness()`) redirect to `/` and are used in place of `requireOnboardedBusiness()`/`getCurrentBusinessId()` in every Estimate/Follow-up/Reply/Analytics page and Server Action, and in the Appointments page/actions, respectively — hitting a disabled route directly redirects home, it doesn't just hide the nav link. `components/layout/nav-items.ts`'s `NAV_ITEMS`/`isNavItemVisible` (shared by `sidebar.tsx`/`mobile-nav.tsx`, threaded down from `app/layout.tsx`) filters the nav the same way. The Dashboard and Settings pages independently skip the irrelevant sections' data fetches and JSX (not just visually hide them) based on the same check. The daily cron (`app/api/follow-ups/generate/route.ts`) filters its business list per job accordingly before calling `runDailyFollowUpJob`/`runDailyReplySyncJob` (skip `appointments_only`) or the four Appointment lifecycle jobs (skip `estimates_only`) — `runGmailWatchRenewalJob` (Gmail push registration, infra-level) runs for everyone. `services/leadService.ts`'s `sendLeadAcknowledgmentEmail` skips calling `createAppointmentFromLead` entirely for `estimates_only` (a booking-shaped message never gets parsed there). "Convert to Estimate" (`components/leads/lead-row-actions.tsx`'s `estimatesEnabled` prop) is hidden, not gated at the action level, for `appointments_only` — the Estimate creation action itself still goes through `requireEstimatesEnabled()` regardless.

**`/appointments` has a List view and a Calendar view, toggled client-side — both read the same server-fetched data, nothing is double-fetched.** `components/appointments/appointments-view.tsx` (client) owns the toggle plus a `selectedDate` filter; `components/appointments/appointment-calendar.tsx` is a month-grid showing every appointment **except `status: 'requested'`** — a requested slot isn't locked in yet, and putting it on the calendar as if booked would contradict this file's "never implies the slot is locked in" rule (steps 1/2 above). Clicking a day sets `selectedDate`, which filters the exact same `AppointmentList`/`AppointmentCard` shown in List view rather than duplicating approve/no-show/cancel/reminder actions inside the calendar itself. All the grid math (which weekday a month starts on, days-in-month, prev/next-month rollover) is pure and framework-agnostic in `lib/calendarGrid.ts` (unit-tested in `tests/calendarGrid.test.ts`), operating entirely in "civil date" integers via `Date.UTC` — never a real Date-as-instant — so it can't be skewed by the browser's own local timezone. Each appointment's calendar bucket (`dateKey`) and chip time (`timeLabel`) are computed server-side in `app/appointments/page.tsx` via `lib/date.ts`'s `zonedDateKey`/`formatZonedTime`, using the business's own effective timezone — same "components stay pure of timezone logic" precedent as `scheduledLabels` already used.

**An `appointments_only` workspace only ever accepts leads/bookings through the website form (`POST /api/intake`) — it never scans the connected Gmail inbox.** `services/gmailLeadCapture.ts`'s `captureLeadsFromGmailForBusiness` early-returns for `productMode === "appointments_only"` regardless of the business's own `monitorGmailInbox` setting — guarded at that leaf function (not just the cron route's business-list filter) so both call sites (the daily cron and the admin's manual "run classification now" button, `app/admin/actions.ts`) are covered. Settings hides the "Monitor Gmail inbox" checkbox and shows Gmail as unavailable in the Lead Sources card for these workspaces, since the toggle would have no effect. Manual Entry and CSV Import stay available in every mode — this restriction is specifically about not reading the connected mailbox's actual messages, not about lead entry points in general.

**Automated emails render as branded HTML, with a plain-text fallback — not plain text only.** `services/gmail.ts`'s `sendEmail` accepts an optional `htmlBody`; when given, it sends a `multipart/alternative` MIME message (plain text first, HTML second) instead of `text/plain` alone — every existing plain-text `body` stays exactly as-is and is what non-HTML clients render. `services/emailTemplates/emailLayout.ts` holds the shared visual language — color tokens, `escapeHtml`, and `renderEmailShell(businessName, innerHtml, accentColor)` (the accent header bar + white card every automated email renders inside, table-based with inline styles throughout since `<style>` blocks, flexbox, and grid are unreliable in Outlook and other mail clients). **`accentColor` is per-workspace, not hardcoded** — `workspaces.email_accent_color` (migration `0021`, nullable hex string) lets a business brand its own automated emails from Settings > Business Profile (a native `<input type="color">`, validated against `config/constants.ts`'s `HEX_COLOR_PATTERN` in `app/settings/actions.ts`'s `updateEmailBrandingAction`); `services/business.ts`'s `getEffectiveEmailAccentColor` falls back to `DEFAULT_EMAIL_ACCENT_COLOR` (a hex approximation of the app's own `--primary`, since `oklch()` isn't supported in email HTML) when unset. Every call site threads the sending business's own effective color through — nothing defaults silently to the app's indigo once a business has set its own. Two builders sit on top of it, chosen by content shape: `renderEmailHtml(businessName, plainBody)` is generic over the `"\n\n"`-paragraph convention every narrative-style template builder follows (escapes HTML, linkifies bare URLs, renders a `complianceFooter.ts` block — detected by its leading `"—"` — as a muted, separated footer) and is used for the customer-facing lead acknowledgment and every Appointment email (`appointmentRequested`/`appointmentConfirmed`/`appointmentReviewRequest`/`appointmentRebookReminder`/`sendReminder`, in `appointmentService.ts`/`appointmentLifecycle.ts`). `services/emailTemplates/leadNotification.ts`'s `buildLeadNotificationEmail` is purpose-built instead, for the one *data-shaped* automated email — the owner-facing "New Website Inquiry" notification (`services/leadService.ts`'s `sendLeadNotificationEmail`) — since a scannable label/value table, a distinct message callout, and a "View lead" button (deep-linking to `/leads/[id]` via `appHost`) serve a fast-scan read better than paragraphs-with-line-breaks; it still renders inside the same `renderEmailShell`. `services/gmail.ts`'s `sendEmail` accepts the resulting HTML as an optional `htmlBody`, sending a `multipart/alternative` MIME message (plain text first, HTML second) instead of `text/plain` alone whenever it's given — every existing plain-text `body` stays exactly as-is and is what non-HTML clients render. **Deliberately not applied to the Estimate Follow-up Queue's `followup_1`/`followup_2`/`final_followup` sends** (`services/followupSender.ts`, `services/microsoftGraphSend.ts`) — those are free-edited, negotiation-style copy and stay plain text; extending this there would also require adding the same HTML support to the Microsoft Graph send path, which hasn't been done.

## Architecture rules

- `/app` — routes and page composition only. No database calls or business logic directly in page components — call into `/services`. Every protected page/action calls `requireOnboardedBusiness()` (or, if it doesn't need the full record, `getCurrentBusinessId()`/`getCurrentSession()`) from `lib/session.ts` and passes `businessId` explicitly into service calls — never assume a global "the business." `requireOnboardedBusiness()` also redirects a business that hasn't finished the onboarding wizard to whichever step it's on — every new top-level authenticated page needs this same guard, not just data-fetching ones.
- `/components` — presentational + client-interactive UI, grouped by domain (`dashboard/`, `estimates/`, `follow-ups/`, `replies/`, `leads/`, `analytics/`, `layout/`, `auth/`, `onboarding/`, `settings/`) plus `ui/` (shadcn primitives, don't hand-edit generated files beyond what's needed). `recharts` is the one charting dependency (used only for the revenue trend line in `components/analytics/revenue-trend-chart.tsx`) — the funnel chart is plain CSS bars, since a proportional bar doesn't need a charting library. Don't add a second charting library; extend with `recharts` if a new chart type is needed.
- `/services` — all external I/O and business logic (Supabase data access, business/tenant CRUD, follow-up generation engine, Google OAuth client, Gmail send/read clients, Calendar client, the approval→send orchestrator, the reply matcher, the Lead lifecycle, the ActivityLog domain layer, the intake request pipeline). Pages and API routes call services; services never import from `/app` or `/components`. Every tenant-owned table's functions in `services/db.ts` take `businessId` as an explicit first parameter — this is deliberate (not solved with implicit/ambient context) so tenant scoping is visible and auditable at every call site. Direct-id lookups (`getEstimate`, `getFollowUp`, `getLead`) additionally verify the fetched row's `workspace_id` matches the caller's `businessId`, since there's no scoping-by-filter equivalent on a direct by-id fetch. Keep `services/gmail.ts` (send), `services/gmailInbox.ts` (read), `services/googleOAuth.ts`, and `services/calendar.ts` pure transport (no database/approval-state knowledge, parameterized with whatever tokens/addresses the caller passes in) — orchestration (retry, token decryption, database sync, stage advancement, reminder create/clear, reply matching/dedup, Lead lifecycle side effects) belongs in `services/followupSender.ts`/`services/calendarReminders.ts`/`services/replyMatcher.ts`/`services/leadService.ts`, not in the transport files. `services/gmail.ts` (send) and `services/gmailInbox.ts` (read) are kept as two separate files on purpose, not one — don't merge them. Same reasoning applies to `services/intakeService.ts` (HTTP-facing: validation/rate-limit/spam/request audit) vs. `services/leadService.ts` (domain: what a Lead's arrival/conversion/archival/assignment/noting triggers) vs. `services/activityService.ts` (thin CRUD-adjacent layer over the durable `ActivityLog` table) — keep that three-way split when extending any of them.
- `/types` — shared TypeScript types/interfaces (`Estimate`, `FollowUp`, `Business`, `Lead`, `ActivityLogEntry`, `Notification`, `SessionPayload`, status enums). Composed read-model types that join multiple entities for one screen (e.g. `leadService.ts`'s `LeadDetail`/`LeadAiInsights`, `analytics.ts`'s `ActivityItem`) live next to the service function that builds them, not in `/types` — that's the existing precedent (`FollowUpQueueItem`, `ReplyInboxItem`, etc. are the exception, not `/types`'s norm).
- `/config` — constants (status lists, default follow-up cadence, Google OAuth scopes/URLs, `APP_TIMEZONE`, `TIMEZONE_OPTIONS`). `DEFAULT_FOLLOW_UP_CADENCE_DAYS` is a fallback — a business's own `followUpCadence*Days` fields (via `services/business.ts`'s `getEffectiveCadenceDays`) take precedence when set. Likewise `APP_TIMEZONE` (`America/Toronto`) is only the fallback when a business hasn't set its own `timezone` (via `services/business.ts`'s `getEffectiveTimezone`) — every business picks its own IANA timezone from the curated `TIMEZONE_OPTIONS` list (Settings/onboarding), used for Calendar reminder times and appointment booking. The daily cron's local-hour filter (`app/api/follow-ups/generate/route.ts`) is written generically (any business at 8am local right now gets processed) but in practice only ever fires for Eastern-time businesses — **Vercel's Hobby plan only allows a cron entry to fire once per day**, so `vercel.json` can only schedule the 2 UTC hours (12:00/13:00, covering Toronto's DST states) that a self-serve-deploy build will actually accept; a business in one of `TIMEZONE_OPTIONS`' other zones will never land on exactly 8am local and never gets this cron's jobs run. Don't reintroduce a multi-hour cron schedule (e.g. `"0 11,12,13,14,15,16 * * *"`) without first confirming the Vercel plan supports it — that exact change silently broke every deploy for several hours before being caught.
- `/lib` — small framework-agnostic-ish helpers (`cn`, formatting, date math). `lib/auth.ts` signs/verifies session JWTs and short-lived OAuth state tokens via `jose` (Edge-runtime compatible, used identically in `middleware.ts`, Server Actions, and the `/api/oauth/google/*` route handlers). `lib/session.ts` is how pages/actions resolve the current business — it independently re-verifies the JWT from the cookie rather than trusting middleware-forwarded headers. `lib/password.ts` hashes/verifies account passwords via Node's built-in `scrypt`. `lib/crypto.ts` encrypts Google refresh tokens at rest (AES-256-GCM, Node's built-in `crypto`) before they're written to the database, which has no field-level encryption of its own — never store a raw refresh token in a plain column. `lib/supabase.ts` is the Supabase client + generic CRUD helpers (see the Database section above). No shadcn re-generation beyond `lib/utils.ts`.
- `middleware.ts` (project root) — verifies the session JWT and redirects to `/login` if missing/invalid/expired. Excludes `/login`, `/signup`, `/api/follow-ups/generate`, and `/api/intake` only. It is a coarse authenticate-or-redirect gate — it is NOT the source of `businessId` for service calls (that's `lib/session.ts`), and it does NOT know about onboarding completeness (that's `requireOnboardedBusiness()`, checked per-page since it needs a database read that doesn't belong in Edge middleware).
- **Google OAuth**: one shared OAuth client (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) serves every tenant's consent flow — `services/googleOAuth.ts` is the only file that talks to Google's token endpoint. A business connects once (from onboarding or Settings) covering Gmail send/read and Calendar scopes together in one grant — don't add a second separate connect flow for Calendar later; reuse the existing refresh token. The OAuth `state` param is a signed, stateless JWT (`createOAuthStateToken`/`verifyOAuthStateToken` in `lib/auth.ts`) carrying `businessId` + `returnTo` — no server-side state store.

Keep TypeScript strict. No `any`. Handle database/env errors at the service boundary with clear thrown errors — don't swallow them silently, and don't add defensive checks for cases that can't happen.

## Access & entitlement

**Access is agency-provisioned, not self-serve — there is no Billing integration in this codebase.** (There used to be: Free/Pro plans gated by a Billing subscription, checkout/billing-portal actions in Settings, and a `/api/webhooks/billing` webhook syncing a `subscriptions` table. All of it — `services/billingService.ts`, `lib/billing.ts`, the webhook route, the `billing` npm package, `plans`/`subscriptions` tables — was removed in migration `0015_workspace_entitlements.sql`. If you ever see a reference to "Pro plan," "checkFeatureGate," or `subscriptionService.ts` elsewhere, that's leftover from before this change.)

**There is no plan/pricing tier in this app — deliberately removed, not merely undocumented.** `workspaces.plan` (`'grow' | 'transform'`) used to decide a seat cap, but the app no longer reads or writes that column: `types/business.ts`'s `Business` has no `plan` field, `services/business.ts` doesn't map or update it, and neither `/admin` page offers a plan selector. The column itself stays on `workspaces` (`not null default 'grow'`, additive-only migration policy — see the Data model section) but is entirely orphaned; don't reintroduce a UI or service function that reads it. If you see a stray reference to "Grow"/"Transform," `WorkspacePlan`, or `PLAN_MAX_USERS` anywhere, that's leftover from before this removal.

The only column on `workspaces` that gates access now, set directly by the agency via `/admin` (see "Admin provisioning" below) rather than a customer ever touching it:
- **`status`** (`'active' | 'inactive' | 'suspended'`, `WorkspaceStatus`) — the actual access gate, checked by `services/business.ts`'s `hasActiveEntitlement`. `'active'` means full access to everything; anything else is a **full app lockout**, not a feature-by-feature restriction — there's no free/fallback tier to drop back to in this model. A new signup defaults to `status: 'inactive'` (see `supabase/migrations/0015_workspace_entitlements.sql`) until the agency flips it.

Team seats are capped independently of any plan concept: `config/constants.ts`'s `MAX_TEAM_SEATS` (currently 3) is a single flat number applied to every workspace, enforced in `services/userService.ts`'s `inviteTeamMember`. Changing the seat cap for everyone means changing that one constant, not adding a tier system back.

The lockout is enforced in exactly one place: `lib/session.ts`'s `requireOnboardedBusiness()` checks `hasActiveEntitlement` **before** the onboarding-completeness check and redirects to `/account-paused` if it fails — since literally every protected page (including Settings, via `requireOwner`) calls this function first, that one check covers the whole app. `app/account-paused/page.tsx` is the one page a non-active workspace can still reach (it calls `getCurrentSession()` directly, not `requireOnboardedBusiness()`, to avoid a redirect loop).

Two other gates key off the same `hasActiveEntitlement` check directly on an already-loaded `Business` (no extra query): `lib/apiAuth.ts`'s `requirePublicApiFeature` (gates the public API's read/manage routes — GET/PATCH on `/api/v1/leads`, `/api/v1/estimates`; POST/webhook lead-creation routes are deliberately never gated, unchanged from before this rework) and `services/webhookDispatcher.ts`'s `dispatchWebhookEvent` (belt-and-suspenders — the customer-facing portal in `app/e/actions.ts` can still trigger a dispatch without going through `requireOnboardedBusiness`, so this one can't rely on the session-level lockout alone). There is no more monthly lead cap — the old Free-tier `maxLeadsPerMonth` limit was dropped entirely; an agency-invoiced flat package doesn't need a metered upsell trigger.

### Admin provisioning

`/admin` (`app/admin/`) is how the agency actually sets `status`/`productMode` in practice — not Supabase Studio day-to-day. Gated by `lib/session.ts`'s `requireAdmin()`, which composes on top of `requireOwner()` and additionally requires `business.id === env.adminWorkspaceId` (`ADMIN_WORKSPACE_ID`) — there's no admin-user table or role/permissions system anywhere else in this app; it's a single deployment-level value naming *the agency's own workspace*, same pattern as `CRON_SECRET`/`GMAIL_PUSH_SECRET`. A customer workspace can never reach it: it's an equality check against one specific workspace id, not a flag a customer's own row could ever satisfy.

Two flows, both in `app/admin/actions.ts`:
- **Activating an already-signed-up workspace** (`updateWorkspaceEntitlementAction(workspaceId, formData)`) — the workspace already has a real owner login from its own `/signup`; this just flips `status`/`productMode`. No invite needed — their existing password starts working the moment `status` becomes `'active'`.
- **Provisioning a brand-new workspace** (`provisionNewWorkspaceAction`) — creates the workspace via `services/business.ts`'s `createBusinessForAgency` (`status: 'active'` set immediately; `password_hash` gets an unguessable random placeholder, same idea as `app/login/actions.ts`'s login-timing `DUMMY_HASH_PROMISE`, since nobody has claimed it yet), then calls `services/userService.ts`'s `createOwnerClaim` to generate a one-time claim link. This deliberately **reuses the team-invite token/expiry infrastructure and the exact same `app/invite/[token]` accept page** — a `users` row with `role: 'owner'` instead of `'member'` — rather than building a parallel invite system. The reuse stops at acceptance: `app/invite/[token]/actions.ts`'s `acceptInviteAction` branches on `member.role` — an `'owner'` claim calls `services/userService.ts`'s `claimWorkspaceOwnership`, which writes the real password onto `workspaces.password_hash` directly and **deletes the transient `users` row**, then signs a normal owner session (no `userId`/`role`) and redirects to `/onboarding/gmail` instead of `/`. After that, the workspace is indistinguishable from one created through self-serve signup — there is no lasting second "owner shape" anywhere in the data model; the `role: 'owner'` `users` row only ever exists transiently, between provisioning and claiming.

Every admin action operates on an explicit target `workspaceId` passed in, never on "the current business" — the only place `requireAdmin()`'s own resolved business matters is verifying the caller is allowed to be here at all (and, for provisioning, as the source of the agency's own name in the handoff email below). This keeps multi-tenant isolation intact: normal app code still only ever touches "your own business," and `/admin` is the one deliberate, explicitly-gated exception.

`provisionNewWorkspaceAction` also renders the client handoff email (`services/emailTemplates/onboardingWelcome.ts`'s `buildOnboardingWelcomeEmail` — same pure `build*` pattern as `acknowledgment.ts`, but a single fixed message, not a per-tenant DB-customizable template) and returns it to `components/admin/provision-workspace-form.tsx` alongside the claim link, always available to copy and send manually. If the agency's own workspace (`ADMIN_WORKSPACE_ID`) has Gmail connected, a "Send email" button also appears — `sendOnboardingWelcomeEmailAction` sends it for real through the *admin's own* connected Gmail (`services/gmail.ts`, the same per-tenant sender every other email in this app uses, just with the admin as the sender instead of the still-Gmail-less new client) rather than the client's, since the client doesn't have one yet — that's literally what the email walks them into. This is a deliberate button click, not fired automatically on every provision. It re-renders the email from its canonical inputs (workspace name/owner/claim URL) server-side rather than trusting client-supplied subject/body text, so the action stays scoped to "send the onboarding email for this workspace" rather than "send arbitrary text through my Gmail." If the admin's Gmail isn't connected, the button is hidden and copy-paste is the only path.

## Team members

A business's own owner login (`workspaces.password_hash`) is unchanged and still the only way to reach Settings. On top of that, an owner can invite teammates (`services/userService.ts`, Settings → Team card) who share full access to estimates/leads/follow-ups/replies/analytics under the same `businessId` — Settings itself (the Google connection, API keys, outbound webhooks, team management) is the one deliberate owner-only boundary (`lib/session.ts`'s `requireOwner`, checked at both the page and every Settings Server Action, since actions are callable independent of which page rendered their form).

An invite is a `users` row with no `password_hash`/`accepted_at` yet and a random opaque `invite_token` (7-day expiry) — `app/invite/[token]` is the public accept page; setting a password fills those in, clears the token, and logs the new member straight in. Each team member has their **own** `session_token_version` (migration 0014), separate from the workspace's — this is deliberate: `workspaces.session_token_version` bumping on the owner's logout must never revoke every invited member's session too, and vice versa (`lib/session.ts`'s `resolveValidatedSession` checks whichever one applies based on whether the session JWT carries a `userId`). The seat cap (`config/constants.ts`'s `MAX_TEAM_SEATS`, flat across every workspace — see "Access & entitlement" below) counts the owner plus every invited-or-pending row, enforced in `inviteTeamMember` — a still-pending invite occupies a seat so a business can't blow past the cap by sending unlimited invites and accepting them all at once. An email can only be one kind of account (owner or member) — `inviteTeamMember` rejects a collision upfront.

No actor attribution exists anywhere yet: `ActivityLog` entries and Leads' `assignedTo` still only know about the business, not which team member did something (see the Non-goals note on `assignedTo`) — that's a deliberate, separate scope boundary, not an oversight of this feature.

## Non-goals for now

- No CRM-style contact management beyond what's on an Estimate record. The reply inbox does NOT change this — replies are surfaced, never turned into tasks/pipelines/auto-actions.
- Leads have exactly two status transitions (`New Inquiry` → `Converted` via the explicit "Convert to Estimate" action, or → `Archived`) — resist adding a general status workflow/pipeline. `assignedTo` is still deliberately a free-text field, not a linked-record assignment to a team member — team members now exist (see "Team members" below) but wiring real assignment is a separate, not-yet-made decision; don't conflate the two. `internalNotes` is a single running log (newest entry first, prepended by `services/leadService.ts`'s `addInternalNote`), not a threaded/multi-author comments system — don't add per-note authorship, edit history, or @mentions without a real reason to (a team member's identity isn't attached to any action anywhere in the app yet — ActivityLog entries record what happened, not who as a distinct user, since businessId was the only actor concept before Team members existed).
- Calendar *reminders* (`services/calendarReminders.ts`) are output-only and always will be — never booking, never checking availability. The one deliberate exception is `services/appointmentService.ts`'s Appointment lifecycle (see the "Appointments" section above) — don't generalize from that back into the reminders file, and don't add a second, general-purpose scheduling/availability feature beyond that one flow without a real reason to.
- **Superseded:** real-time reply sync now exists via Gmail push notifications (`services/gmailWatch.ts` registers a Cloud Pub/Sub watch on the connected mailbox; `app/api/webhooks/gmail-push/route.ts` receives the push and re-runs `services/replyMatcher.ts`'s existing `syncRepliesForBusiness` — no separate matching path). It's an addition on top of, not a replacement for, the daily cron sync and the manual "Check for new replies" button, which both still exist as the fallback for any business without Pub/Sub configured (`GMAIL_PUBSUB_TOPIC`/`GMAIL_PUSH_SECRET` unset — see .env.example) or mid-outage. The watch registration expires ~7 days and is renewed by the same daily cron (`services/gmailWatchSync.ts`'s `runGmailWatchRenewalJob`, piggybacked in `app/api/follow-ups/generate/route.ts` alongside the other daily jobs) and (re-)started the moment Google connects (`app/api/oauth/google/callback/route.ts`). Every failure mode (Pub/Sub not configured, Google API error, unknown mailbox in a push payload) is caught/logged and swallowed — same best-effort philosophy as Calendar reminders/appointment booking — so this can never block Google account connection or make reply sync worse than it was before.
- Reply matching only works when a customer replies from the same address the estimate was sent to, on the existing thread — a reply from a different address or deep in an old part of a long thread won't be matched. Known v1 limitation, not a bug to silently "fix" by loosening the match (that would risk cross-estimate mismatches).
